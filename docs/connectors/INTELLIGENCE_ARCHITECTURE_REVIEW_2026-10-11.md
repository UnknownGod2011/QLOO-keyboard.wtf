## Current path and evidence

Live chooses among three normalized broker tools, not the vendor catalog: resolve, execute, control. There is no separate provider-classification AI request; however, provider choice is still primarily Live tool selection, not a deterministic pre-Live router. Resolve freezes the human request, Firebase-account owner and logical session, asks the authenticated backend for one service's small capability bundle and chooses a verified sole/default provider account or returns choices. Existing task reuse prevents repeated discovery for that same human turn. The backend derives UID from authentication; provider IDs/configs never cross that boundary.

`JarvisConnectorController` owns work, cancellation, activity, write fences and ephemeral result context. Its injected `ConnectorReadReasoner` already provides a provider-independent complex-read worker. It inherits the existing AI owner: Personal reasoning `gemini-3.5-flash`, text `gemini-3.5-flash-lite`, Live `gemini-3.1-flash-live-preview`; no new credential/billing owner. Counts/mixed read plans and writes remain separate proven paths. The reader has 2–8 scoped capabilities, at most four queries/eight executions/nine model turns. Currently it makes a model turn for every execution; ranking/refinement depend on prompt instructions rather than a typed evidence policy.

## Research and decision

- [Anthropic advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use): lazy tool loading and batching deterministic operations can reduce schema and inference overhead. Adopt the patterns, not its provider-specific APIs or arbitrary code execution.
- [Effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents): concise, meaningful retrieval results, progressive detail and evaluations with verifiable realistic outcomes. A successful HTTP call is not goal success.
- [Agent composition](https://www.anthropic.com/engineering/building-effective-agents): choose the smallest effective workflow/agent pattern; framework layers can obscure execution. Preserve the existing injected loop and gateway.
- [Gmail native filtering](https://developers.google.com/workspace/gmail/api/guides/filtering): native `q` supports indexed sender/date/body searches, but API alias expansion/thread-wide matching differs from the UI. Search message candidates then read actual threads; do not assume UI-equivalent fuzzy search.
- [Composio sessions](https://docs.composio.dev/docs/configuring-sessions) and [existing direct integration](https://docs.composio.dev/docs/sessions-vs-direct-execution): current sessions support discovery and account pinning; direct execution remains supported for existing integrations. Our normalized allowlist already isolates the vendor. No migration or unrestricted meta tools merely for elegance.
- [LangGraph replay/idempotency](https://docs.langchain.com/oss/python/langgraph/functional-api): checkpointed results do not make unfinished external writes exactly-once. Keep our durable claim/verification journal and unknown-outcome fence; never replay sends automatically.
- [Microsoft Agent Framework](https://learn.microsoft.com/en-us/agent-framework/overview/): useful state/workflow abstractions, but adopting it would duplicate current task/auth/AI owners. No measured gain supports a new dependency now.
- [MCP tool contracts](https://modelcontextprotocol.io/specification/2025-11-25/server/tools): structured result contracts help interoperability; tool annotations alone are not trusted authorization. No new MCP server is required.

Recommended architecture stays **native hybrid**: existing Jarvis understanding → one provider/account/goal owner → deterministic provider calls and small read-worker decisions → bounded candidate search/refinement → observed-reference content reads → verified grounded answer → independent session-only result context. Public progress is an execution state, never hidden reasoning. Retrieval may resolve approximate names; writes still require an exact, authorized recipient/account and existing permission policy.

## Proven gaps, in priority order

1. **Visual ownership mismatch:** `VoiceOverlayForm.RefreshState` uses health-only `LongTaskDetail` to hide Idle/terminal states; that field intentionally empties between steps. Use the retained visual owner independently, without disabling voice-health checks. Account rebind also clears the display before replacement.
2. **Search previews can masquerade as content:** reader answer validation checks verified receipt references but does not require a content read for a content goal. It can terminate before any search; a cited search can even become the primary mail target. Enforce evidence role and minimum bounded retrieval for negative inferred-search answers; keep goal outcome separate from operation completion.
3. **Inference per tool adds latency:** allow at most two independent search proposals per reasoning turn under the same budgets/account/CTS. Validate the entire batch first, execute serially, never batch writes/counts/pagination. Actual latency improvement requires later real-provider comparison.
4. **Recall depends on a forgotten ID:** allow ID-free read-only recall/open only when the session has one unambiguous retained result. State control, execution/account changes/writes still require an exact ID. Never create new authority from memory.
5. **Transient GET failure ends the server task:** empty-result refinement works; transient read retry does not. A future bounded retry must precede terminalization, recheck cancellation/account/deadline, respect Retry-After, and never include POST/write retries. Do not add replay until this boundary is tested.
6. **General result links/content coverage are incomplete:** exact mail opening has real Chrome proof, other resource references still need provider-specific verified URL adapters. Drive currently supplies metadata, YouTube no transcript/analytics, Discord no messaging. Do not claim these unsupported capabilities through a generic agent.
7. **Fuzzy quality has no real repeatable acceptance:** prompt-only query expansion is not proof. Evaluate typo, vague-topic, long-thread, ambiguity and injected-content cases with known outcomes. At least one second-provider semantic request must pass. Do not download/index the mailbox or use approximate recipients for sends.

## Implemented continuation and exact proof tier

The first bounded source continuation implements gaps 1–4 above, not a new architecture:

- Visibility follows the retained connector visual owner, while between-step response-health detail remains empty. Idle/aged terminal voice states cannot hide the task. Account correction transfers that owner atomically without restarting its display clock.
- One linked cancellation owner fences account handoff. Reset, explicit cancellation, disposal and terminal control cancel it; an uncooperative late rebind cannot create a replacement task. Pruning preserves an active handoff until cancellation/expiry.
- Shared evidence traits distinguish candidate search, actual content and metadata. Content questions need primary content evidence; metadata-only repository/channel tasks do not incorrectly require unrelated issue content. Authoritative blank Doc/Form/mail-content receipts are distinguished from missing content. Verified empty searches cannot support positive matches, and inferred negative answers require bounded refinement.
- One model proposal can contain exactly two independent searches, validated together and executed serially within the same task/account/query/operation limits. Literal Gmail queries, cursors/resource reads, counts and writes cannot be batched. A failed first receipt or cancellation prevents the next dispatch.
- Read-only recall/open may omit an ID only for one unambiguous retained session result. Execution, state changes, account correction and cancellation still need their exact task reference. `evidence_available` means usable verified receipts, not semantic match success; completion/`verified` alone does not certify that the human goal was fulfilled.

## Next causal slice: typed transient-read recovery

The intelligence/lifecycle continuation above is committed as `3a1fb06fc7371eeb06f04e3d8ee8c4228a22fbb8`, protected by `checkpoint/connectors-intelligence-3a1fb06-20261011`. The following separate backend slice closes the initial-dispatch part of gap 5; it does not retry entire capabilities, page continuation or enrichment.

Root cause: every provider exception at the initial read dispatch settled the operation and ended its task. Retrying the normalized `unavailable` code would be unsafe: it conflates project/auth configuration, malformed/oversized envelopes, unknown service failures and transport faults. The adapter now retains **internal typed** transient-read/retry-duration hints only for transport/IO/internal timeout or HTTP 408/429/500/502/503/504. Caller read cancellation propagates; auth/scope, malformed JSON/envelopes, oversized bodies and unknown service errors do not gain retry permission. Customer codes/messages and write ambiguity behavior remain unchanged. Raw headers/payloads are never returned or logged.

Only an existing server-planned, non-write GET with no body may repeat its **initial** dispatch once, using the same operation claim, endpoint, frozen arguments, account and request counter. Default wait 250ms; a supplied wait above two seconds or remaining original deadline causes truthful failure, not an early retry. Invalid/duplicate waits also fail closed. Before recovery the owner rechecks task readiness/expiry/customer/account, verifies the live grant/provider binding, then checks again immediately before dispatch. Second failure uses existing terminal settlement. A cancelled/expired late response cannot publish success. Writes, OAuth, discovery, write reconciliation and continuation/enrichment are not automatically replayed; no AI request or billing owner is added.

Deterministic tests exposed and fixed two local edge cases: a cancelled read with an uncooperative transient exception was classified Failed, and a wrongly typed proxy status escaped normalized error handling. Independent review exposed conflicting duplicate Retry-After headers; these now prohibit early recovery. Original rejected receipts remain retained.
