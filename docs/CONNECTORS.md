## Alternatives and decision

| Option | Quality / latency / cost | Scaling / ownership | Decision |
| --- | --- | --- | --- |
| Small permanent broker | Constant schema cost; lazy discovery needs a tool receipt before execution | Easy server isolation, but an unbounded natural-language broker can hide actions | Use a **bounded normalized** form, not an opaque do-anything agent |
| Dynamic Live injection | Few relevant schemas; potentially one fewer discovery exchange | Current Live setup is built at connection start; altering it risks reconnect/audio behavior | Do not change Live transport for this |
| Server AI planner | Can reason over small tools, but adds inference/latency and another billing owner | Useful later for cloud jobs; unnecessary now | Not in v1 |
| Permanent provider bundles | Direct tool choice, but growing catalog/prompt cost on every turn | Duplicates provider knowledge in Jarvis | Reject permanent bundles; return small task-scoped capability bundles lazily |
| MCP-like boundary | Portable tools, but another server/session/policy layer | Useful for external agent clients, not required for current REST/desktop | Do not add MCP now |
| Hybrid | Existing Live reasoning + deterministic provider hints + lazy 2–8 capabilities | One server gateway, authenticated task/account scope, replaceable provider | **Chosen** |

No claim of measured end-to-end latency is made by this table. Before/after
benchmarks and actual provider timings are acceptance artifacts, not invented numbers.

## Owners and integration boundaries

1. **Connector registry**: one backend definition set drives public catalog,
   names, icons, search words, capability families, environment availability,
   private auth mapping and operation safety metadata. No separate UI lists.
2. **Connection service**: Firebase-derived UID/environment owns connect attempts,
   account refs, verified status, default preferences and cache invalidation.
   Provider status is truth; Firestore is an index/attempt journal, not OAuth truth.
3. **Provider interface / Composio adapter**: only this adapter knows vendor IDs,
   v3.1 API shapes, OAuth URLs and native operation names. Tokens stay at Composio.
   No unrestricted proxy URL or arbitrary provider tool is exposed to clients.
4. **Task gateway**: caller + task + capability + account + explicit authority;
   durable operation claims and sanitized state. No model implementation here.
5. **Jarvis client**: tiny resolve/execute/control boundary in the existing
   action path; existing Live reasons over normalized capabilities/results.
   Reuse existing permission, update admission, activity and announcement owners.
6. **Web/Settings**: render the same normalized catalog/accounts; local search;
   no persistent independent connection cache or raw provider objects.

Keep feature files cohesive. Do not add wrappers for every conceptual arrow,
generic workflow engines, permanent connector content memory or custom connectors.

### Check whether Imran replied to Gmail

Existing Live turn → connector resolve (Gmail explicit, no discovery AI) →
authenticated server task/account choice → 2–4 normalized capabilities → existing
Live reasoning → search/read bounded thread → verified read receipt → answer.
One uniquely identified account/default can be selected automatically; several
unselected accounts need a short clarification. Metadata can be cached; email
bodies cannot be cached indefinitely. This native path has no additional
dedicated AI planner; complex read goals may use the bounded read reasoner
described above through the existing AI owner.

Gmail search can return a headers-only sample across its first bounded page:
six messages by default, hard maximum eight, at most three parallel reads and a
four-second optional metadata deadline. Continuation pages default to no sample;
`metadataLimit=0` keeps a verified count-only query to one provider request. This
is part of the same owned operation and its provider-request telemetry, not a new
planner or tool. Samples contain only independently matched message/thread IDs,
From, Subject and Date; they do not prove the bodies or the entire category.
Incomplete samples are marked partial. Explicit queries, quotes and filters retain
exact semantics. The desktop derives `matchMode` from the frozen human turn only
when the backend advertises support; a topic search may refine one empty simple
AND/phrase query into its original words as alternatives, preserving all filters.
The returned `queryUsed` and `refinedEmptySearch` expose that change. It never
refines nonempty results, continuation queries or existing Boolean expressions.
Metadata is not stored in the journal; failures cannot return the first raw receipt.

`mail_count` is a fourth task-scoped read capability, not a permanent Live tool.
It follows at most ten 500-message pages inside one owned operation, deduplicates
message references and returns compact counting evidence without message bodies.
Each additional dispatch rechecks authority. A twenty-second continuation window,
page limit, cycle, rate limit or outage yields an explicit partial/lower-bound
result with a cursor, never a false whole-query total. Counting from a cursor is
also labelled a window, not the total. Counts prove the supplied query, not the
semantic category or an atomic mailbox snapshot. The model still needs to define
category queries from observed headers/bodies. The native counting operation adds
no AI planner/charge; optional owned interpretation is a separately metered AI
call when its narrow inferred-count recovery conditions apply.
Oversized/inaccessible mail bodies are marked incomplete rather than silently
reported as complete empty text. Real natural-query acceptance remains separate
from these source contracts; see the [9 October reliability checkpoint](connectors/GMAIL_RELIABILITY_2026-10-09.md).

## Data/API/OAuth lifecycle

- Stable provider user identity incorporates environment + Firebase UID (not email).
  Server ownership is checked on every account, attempt, task and execution.
- Opaque random application connection/account references; provider IDs kept server-side.
- Connection states: available, connecting, connected, expired, revoked,
  reconnect-required, disconnected, unavailable. Include verification timestamp;
  a provider outage means unavailable/unknown, not a stale Connected checkmark.
- Multi-account model from day one; optional explicitly selected default. Same
  Firebase account on web/multiple PCs reads the same authoritative service.
- `/v1/connectors`: catalog, connections, connect initiation/status/completion,
  reconnect/disconnect/default selection; resolve/execute/task status/cancel.
- Connect initiation has a durable single-flight claim with a stable request ID.
  If creation's acknowledgement is lost, reconcile; do not create another OAuth flow.
- Final return is canonical `/connectors`; `/settings/connectors` remains an alias.
  Random attempt/state bound to authenticated UID, provider and environment.
  Callback parameters alone never establish Connected. Replayed completion must
  be harmless and ownership checked. Pending/expired flows stay truthful.
- Desktop opens the normal default browser to the branded management/consent
  flow. Account mismatch is shown rather than connecting someone else's account.
  Settings refreshes on focus/open; web refreshes after mutations. Do not poll all
  accounts during ordinary Jarvis turns.
- Disconnect verifies ownership, stops new claims, revokes/deletes the provider
  connection, verifies absence and invalidates state. Account deletion performs
  the same cleanup, including pending OAuth attempts, with retryable progress.

## Task, safety, retention and metering

One stable task/request owner: created → routing → ready/planning → executing →
verifying → completed/failed/cancelled/outcome-unknown. Terminal owners cannot
resurrect or publish over a newer owner. Speech barge-in is not task cancellation;
explicit cancel/replacement/session shutdown is. In-flight writes cannot be unsent.
Task account corrections are safe only before dispatch; afterward explain outcome.

The existing ordered assistant-answer boundary also ends a settled desktop task
when every operation has completed and its actual result was delivered. It does
not depend on the model remembering a final `connector_control complete` call.
Pending confirmation, in-flight operations and unread background results remain
owned. Match the turn that received the result (including a later confirmation
or retrieval), while keeping the original user identity/write fence immutable.
An unrelated answer cannot end the task; completed controls cannot republish old
content or restart an action. This hook makes no connector request when no task
exists and does not alter Live/audio, selection or other action ownership.

Durable operation claim binds UID/environment/account/capability/argument digest.
Provider idempotency/operation IDs used where available. For email use a stable
message identity and reconcile sent evidence. A durable claim alone does not prove
exactly-once *effect*: unknown outcomes must not be automatically retried.

No email/message/document bodies in persistent task journals, logs or preferences.
Only bounded current-session model context/results; clear at session end. Keep
sanitized task metadata briefly, connect state until expiry, connection metadata
until disconnect/account deletion; configure and verify actual TTL before release.
Never retain credentials in API responses, browser storage, docs or source.

Connector API calls do not call AI reservation/settlement. Existing Live inference
remains billed normally once by its bound owner. The bounded desktop read reasoner
and optional count interpretation reuse the existing AI gateway and inherited
Personal/Managed owner; actual additional model calls are metered once, not treated
as free connector execution. No separate server AI planner or Composio NLP shortcut
is introduced.

Telemetry target: shared request/task ID, safe user/account reference,
provider/capability, stage/call count/elapsed/status/normalized error; never bodies,
tokens or raw errors. Current execution logging and durable journals establish
operation/capability/state/elapsed and task/account ownership. The real logical
Live conversation ID is now captured once as bounded client-origin diagnostic
metadata, alongside server-derived UID/auth-session hashes and actual provider
action/verification attempt counts. It is not action authority or a billing ID.
**A server-verified join to the Managed physical billable request is still not
implemented/proven.** Do not call the diagnostic correlation fully linked billing
telemetry or alter reservation/settlement to conceal this remaining release gate.
